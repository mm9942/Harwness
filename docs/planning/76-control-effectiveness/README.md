# Control infrastructure — effectiveness review

Scope: the parts of harw that steer agents toward a result — context
assembly (`harw-core/src/model.rs`, `turn_loop.rs`), tool dispatch, the
WorkDriver loop (`harw-plan-bridge/src/work_driver.rs`,
`harw-cli/src/job_worker_work_driver.rs`), delegation (`delegate_wave`) and
the build/CI gate. Everything below was checked against HEAD (`90160f4`).
Items already on the R1–R11 roadmap in
[75-harness-patterns](../75-harness-patterns/README.md) (cost model, hooks,
ledger, scheduler, headless) are not repeated.

The design invariants (authority only narrows, deny wins, the model never
achieves a goal, fail closed) are sound and stay. The problems are in what
the agents **see** and how fast the loop **turns**.

## Summary (ranked by impact)

| # | Finding | Effect | Status |
|---|---|---|---|
| F1 | `Cargo.lock` on `main` contains 129 merge-conflict blocks | nothing builds or tests on `main` | **fixed in this branch** |

| F3 | WorkDriver workers get only the last 5 stderr lines of a failed verification | workers cannot see which test/line failed; feedback goes to every worker | **fixed in this branch** |
| F4 | A verify-only round counts against `max_iterations` | the default 8 rounds buy ~3–4 fix cycles | proposal |

| F7 | Parallel tool dispatch is all-or-nothing per model response | one `fs.write` among five reads serializes all six | proposal |
| F8 | CI is `workflow_dispatch` only | F1 landed unnoticed | proposal |

## F1 — broken lockfile on `main` (fixed)

Merge `9e639f5` (`release/0.9.1` → `main`) committed 129 conflict blocks
into `Cargo.lock`, all of the form `0.9.0` vs `0.9.1` for workspace
crates. Cargo refuses to parse the file, so `cargo build/test/clippy` fail
on `main`, and every release job (`--locked`) would fail too.

Fix: take the `release/0.9.1` side (the workspace version is `0.9.1`), then
let Cargo complete the file. Cargo changed only workspace members
(three crates still at `0.9.0`, and `harw-tool-tunnel`, which was missing).
No external dependency moved; `cargo metadata --locked` passes.

## F2 — context never reaches the model (highest leverage)

`turn_loop::build_model_request` gathers every `ContextProvider` fragment
and calls `ModelRequest::with_context_program(…, program, ceiling)`
(`harw-core/src/model.rs:291`). Two paths:

1. **Program and ceiling present:** instruction-trust fragments are
   appended to `system_prompt`; data/evidence fragments go into
   `data_block`. The OpenAI-compatible builders read `data_block`
   (`harw-provider-http/src/lib.rs:2887,3643`). **`anthropic.rs` does
   not** (`build_messages_body`, `anthropic.rs:564`), so on Anthropic every
   data fragment is dropped even here.
2. **Otherwise** (`model.rs:364`): fragments go into
   `ModelRequest::context`. The module's own doc (F-016/G-023) states that
   no wire builder reads that field. Verified with a probe test: a fragment
   on this path appears in none of `system_prompt`,
   `instruction_fragments`, `data_block` or history.

Path 2 is the common one. It is taken whenever the session has no
declared `[context]` program **or** runs under a closed ceiling:

- the UIA generated by `harw-cli/src/uia_bootstrap.rs` (no program);
- 13 of the 26 built-in agent definitions (all `uia-*`, `researcher`,
  `memory-steward`, `agent-steward`, `cargo-worker`, …);
- every closed-ceiling entry (web, MCP, jobs, gateways —
  `harw-runtime/src/assembly.rs` `root_context_program`), which includes
  **every WorkDriver worker**.

What is lost on that path: `MemoryFactsContextProvider`,
`RepoTreeContextProvider`, `PinnedPlanContextProvider`,
`GoalContextProvider`, `HandoffContextProvider`, `ProjectContextProvider`,
`WorkbenchContextProvider`, SDK context providers — and the turn loop's own
instruction fragments `budget.wrap_up` (Teil C) and the max-tokens
`continuation.instruction`, which ride in the same vector.

The existing test
`test_with_context_program_without_program_matches_with_context_budget`
pins the fallback to the legacy output, so the drop is protected by a test
rather than caught by one.

**Proposed fix (two small, separate changes):**

1. `anthropic.rs`: emit `data_block` the way the chat builder does — a
   `user` text block after the last `tool_result` (it then sits after the
   cache breakpoint on the previous message, so caching is unaffected).
2. `model.rs` fallback: run the fragments through the same trust split as
   the program path — `Instruction` → appended to `system_prompt`,
   everything else → `data_block` — bounded by `budget.max_context_bytes`
   instead of the program/ceiling admission. Replace the
   "byte-identical" test with one that asserts each trust class lands in
   its wire field, and add one end-to-end test per wire builder
   (fragment in → marker in serialized body).

Watch-outs: this changes prompts for most sessions, so measure token use
before/after; keep volatile fragments (goal state, plan) out of the
system prompt (they are `Data`/`Fresh`, so they go to `data_block` at the
tail — cache-friendly).

## F3 — blind workers (fixed)

`report_from_run` kept the last 5 non-empty **stderr** lines per failed
step. For `cargo test` the failures (test name, panic location, assertion)
are on **stdout**; the stderr tail is `error: test failed, to rerun pass
…`. For compile errors the tail is `error: could not compile … due to N
previous errors`. Neither names a file, so `failing_lines_for` broadcasts
the line to every worker — and workers may not build (DEC-004), so they
cannot find out themselves. The executor already captures 64 KiB of
**both** streams (`DEFAULT_OUTPUT_TAIL_BYTES`); the data was thrown away.

Fix: `harw-cli/src/job_worker_verify_diagnostics.rs` extracts rustc
diagnostics (`error[E…]: … at path:line:col`) and test failures
(`test <name> failed at path:line:col: <message>`, both panic formats)
from stdout and stderr, drops summary lines, deduplicates, caps at 20
lines × 300 chars, and falls back to the old stderr tail when nothing is
recognized. Paths stay workspace-relative, so routing now reaches the
owning worker.

## F4 — verify-only rounds eat the iteration budget

`decide` emits `Verify` only when the wave is already settled at decision
time (`drive_settled_wave`, `work_driver.rs:952`), so the sequence is
*round n: workers* → *round n+1: verify only* → *round n+2: fix*.
`drive_round` increments `iteration` for both. With `max_iterations = 8`
a run gets ~3–4 fix cycles (one fewer if the judge runs).

`execute_steps` already supports running `Verify` after the wave in the
same round (`after_wave`). Proposal: after `execute_wave`, if every worker
of the run is settled and verification is `NotRun`, run the verification
in the same round. Keep `decide` pure; the change is in the executor.
Alternative with zero behavior change in `decide`: do not increment
`iteration` on rounds whose only step is `Verify`/`Judge`.

## F5 — barriers and serial workspace scopes

`execute_wave` (`job_worker_work_driver.rs:1189`) splits a wave into
chunks and awaits each with `join_all` (`:1250`): a chunk waits for its
slowest worker before the next chunk starts. `delegate_wave` already uses
a rolling pool for exactly this reason.

`chunk_end` (`:1157`) also cuts a chunk at the second workspace-scope
worker, and every command-only criterion gets its **own** workspace scope
(`test_command_only_criteria_get_separate_workspace_scopes`). A goal whose
criteria are all "`cargo test -p X` passes" therefore runs one worker at a
time.

Proposal: (a) rolling pool with the same pacing and write-scope check per
completion; (b) derive a scope from the command where possible
(`cargo test -p <crate>` → `<crate dir>`), and merge the rest into one
workspace scope instead of N serial ones. (b) depends on F6.

## F6 — write scopes enforced after the fact

Workers' `owned_paths` reach the model only as a prompt sentence
(`worker_identity`, `:2803`); the sandbox grants `WriteWorkspace` for the
whole tree, and a write outside the scope is detected by a workspace
snapshot diff after the chunk — then **every worker of the wave is set to
`Blocked` and the run escalates to a human**.

All worker writes go through in-process tools (`fs.write`, `fs.edit`,
`doc.*`, `deps.*`), which already reject protected paths
(`protected_component`, `harw-tool-fs/src/write.rs:80`). Proposal: carry
an optional write allowlist (`PathRule`s, plus a deny list for foreign
paths) in the tool execution context and check it next to
`protected_component`. The model gets an immediate tool error it can
correct; the snapshot diff stays as defense in depth. This also makes
concurrent workspace-scope workers attributable, removing the reason for
the one-per-chunk cut in F5.

## F7 — all-or-nothing parallel dispatch

`try_execute_parallel_calls` (`turn_loop.rs:6113`) runs a response
concurrently only if **every** call is parallel-safe; otherwise the whole
response goes sequential. Proposal: split the call list into maximal runs
of parallel-safe calls separated by barrier calls, execute runs
concurrently and barriers in order. Order of results in history is
unchanged; approvals keep their per-call preflight.

## F8 — no automatic gate

`.github/workflows/ci.yml` is `workflow_dispatch` only by design. That
design is fine for the expensive jobs, but F1 shows the cheap invariants
need a trigger. Proposal: a separate, seconds-long workflow on `push` and
`pull_request` that runs only `cargo metadata --locked`, a conflict-marker
grep and `cargo fmt --check`. It never builds, so it does not conflict
with DEC-004.

## How to measure the gain

The WorkDriver state sidecar already holds most of what is needed. Track
per run: rounds to green, tokens per met criterion, the share of failing
lines that were broadcast (no path match) vs routed, cache hit ratio per
worker, and serial vs parallel worker-seconds per wave. F3 should show up
immediately as a drop in broadcast share; F4/F5 as fewer rounds and lower
wall time; F2 as fewer exploratory reads per turn.
