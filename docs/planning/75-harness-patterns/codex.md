# Codex → harw Provider Mapping (synthesis)

Repo root: `/home/user/Harwness`. All paths below are relative to it unless given in full.

## A. Codex capability summary

**Headless / JSON events.** `codex exec` is a subcommand of the single `codex` binary (own `Cli`, `codex-rs/exec/src/cli.rs`), inheriting only `SharedCliOptions` (model, sandbox_mode, cwd, add_dir, oss, profile, worktree, bypass-approvals) from the root command. `--json`/`--experimental-json` emits a JSONL `ThreadEvent` stream: `thread.started, turn.started, turn.completed, turn.failed, item.started/updated/completed, error`, with item kinds `agent_message, reasoning, command_execution, file_change, mcp_tool_call, collab_tool_call, web_search, todo_list, error` (`codex-rs/exec/src/exec_events.rs`, confirmed against `main`, no pinned SHA for the first pass; commit `88235f8` for the later pass). Exit codes are effectively binary (0 / 1 via `error_seen`); interrupted/failed turns are not fully reliable signals (open issues #4721, #41984) — a consumer must parse the JSONL, not trust the exit code alone. `codex exec` has no `--ask-for-approval`; it hardcodes `AskForApproval::Never` for headless runs (`codex-rs/exec/src/lib.rs`).

**Structured output.** `--output-schema <FILE>` attaches a JSON Schema to the Responses API `text.format` field. Confirmed caveats (community-filed, unconfirmed-fixed): gated to a `gpt-5`-like model family (#4181), applied to intermediate messages too (#19816), and `codex exec resume` doesn't support it (#22998).

**Sessions/resume.** Rollouts persist at `$CODEX_HOME/sessions/YYYY/MM/DD/rollout-<ts>-<id>.jsonl`, compressed to `.jsonl.zst` after 7 days (`codex-rs/rollout/src/{lib,recorder,compression}.rs`). `codex exec resume [SESSION_ID|--last|--all]`, `fork`, `--ephemeral` (no persistence, resume then likely creates a new session — third-party-observed, unconfirmed in source). SQLite-backed `state_db`/`session_index` modules exist for listing/search but weren't read in depth.

**MCP — client only.** `codex mcp {list,get,add,remove,login,logout}` manages **outbound** connections in `[mcp_servers.<name>]` (stdio or Streamable-HTTP, `rmcp` 3.2.0, spec 2025-06-18). Startup timeout 30s / tool timeout 300s defaults (`codex-rs/codex-mcp/src/rmcp_client.rs`), per-tool approval modes `auto|prompt|writes|approve`, oauth/chatgpt/ema_auth. **No `codex mcp-server`/serve subcommand exists in current source** — the "codex()/codex-reply() as MCP tools" pattern from older writeups was not found; grep for `mcp-server`, `codex_reply` was empty outside doc redirects. The programmatic surface today is a separate JSON-RPC 2.0 daemon, `codex app-server` (large method surface: `thread/*, turn/*, hook/*, mcpServer/*, account/*, plugin/*, thread/goal/*`), not itself an MCP server.

**Sandbox/approvals.** `SandboxMode {read-only(default), workspace-write, danger-full-access}`; `AskForApproval {untrusted, on-request(default; on-failure is now just a deserialize alias into it), granular{sandbox_approval,rules,mcp_elicitations,request_permissions,skill_approval}, never}`. A newer `[permissions.<name>]` system (`:read-only`/`:workspace`/`:danger-full-access` built-ins, `extends`-based inheritance) layers on top. Linux enforcement is primarily bubblewrap (mount namespaces); Landlock is legacy/fallback only, plus seccomp for network/AF_VSOCK. macOS uses Seatbelt `.sbpl` profiles. All `codex-rs/{config,protocol}/src/*` (confirmed).

**SDK / app-server.** `@openai/codex-sdk` (TS) spawns the CLI and speaks the same JSONL over stdio (`startThread`, `thread.run({outputSchema})`, `runStreamed`, `resumeThread`). A Python SDK exists (`sdk/python`) but its API wasn't read. `codex app-server` is the richer, persistent alternative for multi-turn/session-aware integration — its exact wire semantics beyond method names weren't pulled in this pass.

**AGENTS.md.** Global: `$CODEX_HOME/AGENTS.override.md` > `AGENTS.md` (`codex-rs/codex-home/src/instructions/mod.rs`, confirmed). Nested per-directory discovery order is documented on developers.openai.com but wasn't re-verified against source.

**Hooks/notify.** 12 lifecycle events (`PreToolUse, PostToolUse, PermissionRequest, PreCompact, PostCompact, SessionStart, SessionEnd, UserPromptSubmit, SubagentStart, SubagentStop, Stop, Interrupt`, `codex-rs/hooks/src/schema.rs`). The wire format is **deliberately Claude-Code-compatible**: same camelCase output shape, the same `permission_mode` enum (`default/acceptEdits/plan/dontAsk/bypassPermissions`), `CLAUDE_PLUGIN_ROOT`/`CLAUDE_PLUGIN_DATA` env vars "for OOTB compat with existing plugins", and an internal type literally named `ClaudeHooksEngine`. Legacy single-command `notify` still exists (`agent-turn-complete` JSON payload). A native goal/continuation extension, `codex-rs/ext/goal` (`update_goal` tool, `continuation.md` prompt template, `thread/goal/{set,get,clear,updated}` RPCs), is Codex's own in-model analog of "block until a goal holds" — implemented as a tool+prompt-template loop, not an external process gate.

**Telemetry/usage.** `turn.completed.usage = {input_tokens, cached_input_tokens, cache_write_input_tokens (optional/later-added), output_tokens, reasoning_output_tokens}` — no `total_tokens`, no dollar cost. Rate limits are **not** in the `--json` stream at all, and per issue #14728 even the internal `TokenCountEvent.rate_limits` is reportedly `null` for exec-mode sessions — rate-limit visibility for headless automation is currently weak/unreliable. `codex-otel` crate provides OTel trace/log/metric export (`[otel]`, explicitly denylisted from project-local config for supply-chain reasons).

## C. Codex-as-backend vs native API calls

Two independent axes, not mutually exclusive:

1. **Native provider calls (current, `harw-provider-http/src/codex.rs`).** harw talks directly to `https://chatgpt.com/backend-api/codex` (or `api.openai.com/v1`) over the Responses API, reusing the *ChatGPT/Codex CLI's own login* (`~/.codex/auth.json`) via `harw-oauth/src/codex_refresh.rs`. **Trade-offs:** thinnest integration (one `ModelProvider` impl), fully under harw's own concurrency/budget/sandbox control (DEC-003/DEC-007), no subprocess management — but it depends on undocumented/provisional wire details the code itself flags as provisional (`OpenAI-Beta`, `session_id` headers in `login_headers`, marked "not derived from a verified source" in `codex.rs` comments), and rides on an authentication surface (ChatGPT backend-api) that isn't OpenAI's publicly documented API, so it can break without notice and sits closer to ToS-sensitive territory (using a CLI's login token from a different client, `originator` header) — see DEC-... style caution already written into `provider_toml.rs`'s doc-comment on `originator`.

2. **`codex exec --json` as a subprocess worker.** harw would spawn `codex exec --json [--output-schema FILE] [-C cwd] [-s sandbox_mode]` per task and parse the JSONL (`thread.*`/`turn.*`/`item.*`) instead of calling the Responses API directly. **Trade-offs:** gets Codex's own sandboxing (bubblewrap/Seatbelt), its own approval defaults (`Never` in headless mode — matches harw's own headless posture), its own session/rollout persistence, and `--output-schema` for structured output "for free" — but: adds a process-management layer harw would need to fit into its existing `harw-agent-runner`/`child_protocol.rs` (translating Codex's JSONL into `SdkEvent` rather than inventing a third event shape), inherits Codex's own reliability gaps (rate limits null in exec mode, exit codes not fully trustworthy, `--output-schema` caveats), and requires whatever `codex` binary/version is installed on the host — a dependency harw doesn't otherwise have. Best fit for a mode where the *point* is to exercise Codex's own sandbox/approval/session machinery (e.g. a "run this exactly as the Codex CLI would" verification path), not for harw's own gap-hunt orchestration, which already gets its goal-loop/subagent/rate-limit machinery from `harw-plan-bridge`/`harw-agent-runner` independent of either provider.

3. **`codex mcp-server` as a tool — not available.** The research found no such subcommand in current source; this option doesn't exist today. The closest thing, `codex app-server`, is a JSON-RPC daemon with its own protocol, not an MCP server — using it would mean writing a *bespoke* client against `codex-rs/app-server-protocol`, not reusing `harw-mcp-client`.

**Recommendation:** keep native API calls (option 1) as the default path harw's own orchestration drives, since it's already wired into every provider-neutral abstraction listed in B. Reserve option 2 (subprocess `codex exec`) for a narrowly-scoped, opt-in "delegate this task to the real Codex CLI" worker mode, gated the same way `harw-sandbox`/`harw-job-exec` gate any other host process (`SandboxRequirement`, `ChildRights`), and explicitly not on the hot path of the gap-hunt work driver.

## D. Risks and open questions

- **Auth surface stability.** `codex.rs`'s `login_headers` sends `OpenAI-Beta`/`session_id` values the code itself marks provisional/unverified against current `codex-rs`. This is the single most likely thing to silently break on a Codex CLI update; needs a recheck against `../codex` (if attached) on every provider-limits review, not just once.
- **ToS/policy exposure.** Using the Codex CLI's own ChatGPT login from a different client (`originator` header, `harw-config/src/provider_toml.rs` doc-comment already flags this) is a user choice harw deliberately doesn't force either way — but it's a standing legal/ToS risk the DEC docs should keep naming explicitly, especially if `originator` is ever set to mimic the official client.
- **Rate-limit blindness on the Codex route.** Per the research, `chatgpt-account-id`/`chatgpt.com/backend-api/codex` rate-limit signal reliability is unconfirmed, and Codex's own exec-mode rate-limit reporting is reportedly broken (#14728). `ProviderRateLimiter::observe_headers`'s OpenAI-style header parsing may simply never fire on this route — DEC-003's config-driven `max_concurrency`/budget become the *only* real control, not a backstop.
- **Structured-output gap.** Until `ModelRequest` carries an `output_schema`, harw's `ReturnPipeline.contract` remains a post-hoc, best-effort convention for every provider, not just Codex — this is a general harw gap the Codex research happens to surface clearly (Codex's own `--output-schema` has the same reliability caveats, so parity, not superiority, is the realistic goal).
- **API stability generally.** Nearly every Codex fact above is sourced from `main`-branch code fetched 2026-09-27 (commit `88235f8` for the later batch), with no pinned release tag for the first batch, against a CLI shipping near-daily (`0.157.1` → `0.159.0-alpha.9` in 24h per the research). Any harw code that encodes Codex wire details (`codex.rs`, `codex_refresh.rs`) should carry an explicit "verified against commit X" marker and a recheck cadence, not just a fetch date in a comment.
- **Unverified in this pass:** exact `codex app-server` wire semantics beyond method names; whether the `apply_openai_family` header parser in `rate_limiter.rs` actually receives anything from the ChatGPT backend route (needs a live capture, not just source reading); whether `--ephemeral`/resume interaction is as described (third-party-sourced only); Python SDK API surface (unread).
