# Migration Guide: 0.1.0 → 0.2.0

This guide targets downstream consumers of `harw-ops`, `harw-tui`, and
`harw-core` who were building against the 0.1.0 release series.

---

## 1. Workspace version alignment

In 0.2.0 all `harw-*` crates adopt `version.workspace = true`. If your
`Cargo.toml` pinned individual crates, replace each pinned entry with the
shared workspace version:

```toml
# 0.1.0 style — separate per-crate pins
[dependencies]
harw-ops    = "0.1.0"
harw-core   = "0.1.0"
harw-tui    = "0.1.0"

# 0.2.0 style — one version controls all
[dependencies]
harw-ops    = "0.2.0"
harw-core   = "0.2.0"
harw-tui    = "0.2.0"
```

If your workspace re-uses the version via `version.workspace = true`, add
`harw-*` to the `[workspace.dependencies]` table at the root and reference it
from each member without a hard-coded version string.

---

## 2. `OperationRegistry::register` → `try_register`

`register` previously panicked silently on duplicates in some code paths.
In 0.2.0 the canonical API is `try_register`, which returns
`Result<(), RegistryError>`.

```rust
// 0.1.0
registry.register(meta);

// 0.2.0
registry.try_register(meta)?;
// or, if panic-on-duplicate is acceptable in a binary setup path:
registry.try_register(meta).expect("duplicate operation registration");
```

`RegistryError` variants:
- `DuplicateName` — canonical name already registered (case-insensitive).
- `AliasCollision` — an alias conflicts with an existing name or alias.
- `SelfCollision` — an alias duplicates the operation's own canonical name.

---

## 3. `CommandRegistry::from_operation_registry` now returns `Result`

```rust
// 0.1.0
let cmd_registry = CommandRegistry::from_operation_registry(&op_registry);

// 0.2.0
let cmd_registry = CommandRegistry::from_operation_registry(&op_registry)?;
// or
let cmd_registry = CommandRegistry::from_operation_registry(&op_registry)
    .expect("command registry build failed");
```

The error type is `TuiRegistryError`. Most call sites that build the registry
once at startup should simply propagate via `?`.

---

## 4. `AgentArgs / SkillsArgs / PluginsArgs` field rename

The single `cmd: Option<String>` field that held a joined argument string is
replaced by three typed fields: `action`, `target`, and `value`.

```rust
// 0.1.0
match args.cmd.as_deref() {
    Some("stop <id>") => { /* manually split */ }
    _ => {}
}

// 0.2.0
match (args.action.as_deref(), args.target.as_deref()) {
    (Some("stop"), Some(id)) => { /* id is already extracted */ }
    _ => {}
}
```

Any code that pattern-matched or destructured the old `cmd` field must be
rewritten to use `action / target / value`.

---

## 5. `TuiSessionController` — no longer constructed per command

In 0.1.0 a fresh controller was created inside each command handler. In 0.2.0
the controller is a long-lived `Arc<TuiSessionController>` owned by `ChatApp`.

```rust
// 0.1.0 — inside a command handler
let controller = TuiSessionController::new(config);
controller.apply(change);

// 0.2.0 — access via ChatApp
let controller = Arc::clone(&app.session_controller());
controller.queue(change);
// state is applied at the next safe turn boundary automatically
```

Do not create a new `TuiSessionController` per command. Doing so will lose
queued state between commands and bypass the turn-safe application hook.

---

## 6. `AgentSession` new fields

`AgentSession` gained two optional fields: `active_model: Option<ModelId>` and
`active_provider: Option<ProviderId>`. If your code constructed an `AgentSession`
via a struct literal, the build will fail with missing fields.

```rust
// 0.2.0 — use builder methods or Default
let session = AgentSession::default()
    .with_active_model(Some(model_id))
    .with_active_provider(Some(provider_id));

// or, if you need only some fields set:
let session = AgentSession {
    active_model: None,
    active_provider: None,
    ..Default::default()
};
```

---

## 7. `ModelRequest` new fields

`ModelRequest` gained `model_id: Option<ModelId>` and
`provider_id: Option<ProviderId>`. Struct-literal constructions will fail to
compile without these fields.

```rust
// 0.2.0
let req = ModelRequest {
    // ... existing fields ...
    model_id: None,
    provider_id: None,
};
// or use the builder:
let req = ModelRequest::builder()
    .model_id(Some(model_id))
    .provider_id(Some(provider_id))
    .build();
```

---

## 8. `harw-model-catalog` — `ProviderId` and `ModelId` are now newtypes

`harw-model-catalog` previously exposed `pub type ProviderId = String`. In
0.2.0 both types come from `harw_types`:

```rust
// 0.2.0 import
use harw_types::{ModelId, ProviderId};
```

The newtypes implement `Deref<Target = str>`, `AsRef<str>`, `Borrow<str>`, and
bidirectional `PartialEq<str / &str / String>`, so most existing code compiles
unchanged. The main breakage surface is construction:

```rust
// 0.1.0
let pid: ProviderId = "anthropic".to_owned();

// 0.2.0
let pid = ProviderId::from("anthropic");   // preferred
let pid: ProviderId = "anthropic".into();  // also works
```

---

## 9. `/model` and `/provider` unknown subcommands now error

In 0.1.0 an unrecognised subcommand (e.g. `/model frobnicate`) silently fell
through to the `show` handler. In 0.2.0 it returns `InvalidArguments` listing
the supported subcommands.

If you have scripts or test fixtures that relied on the silent fallback, replace
them with an explicit `show`:

```
/model show
/provider show
```

---

## 10. Recommended entry point: the `harw` facade crate

For new consumers, import from the `harw` facade instead of individual crates:

```toml
[dependencies]
harw = "0.2.0"
```

```rust
use harw::prelude::*;
```

The facade re-exports canonical types from `harw-extension-api`,
`harw-operations`, `harw-ops`, `harw-agent-dsl`, `harw-core`, `harw-provider`,
`harw-model-catalog`, `harw-registry-defaults`, and `harw-types` under stable
module paths. See `harw/examples/minimal.rs` for a runnable introduction.

---

## What to expect next in 0.2.0-beta

The following areas are known unstable in 0.2.0 and will stabilise in a
later 0.2.x pre-release:

1. **`Harness::builder()` fluent API** — a typed, ergonomic builder for
   constructing a harness from configuration will land before beta.
2. **Typed Parent-to-Child return pipeline** — the Agent-as-Tool pattern
   currently returns a plain string; typed fachliche return values are
   in design.
3. **Full IR-to-Runtime consumption** — `ExecutableAgentIr` exists but the
   runtime still reads `AgentRole` from `harw-types` directly; the IR will
   become the canonical runtime input before stable.
4. **Goal-driven compute layer** — `GoalGraph`, `FinalObjective`, and
   `GoalEvaluator` types are architecture stubs; the long-horizon planning
   runtime is deferred past alpha.
