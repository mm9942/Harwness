### dep-request (nicht selbst ausgeführt, nur vermerkt)

`cancel.rs` (von C-CANCEL parallel geschrieben) nutzt `tokio_util::sync::CancellationToken`
(`harw-core/src/cancel.rs:68`), eine Dependency, die noch **nicht** in `harw-core/Cargo.toml` steht.
Diese Datei durfte laut Brief nicht angefasst werden außer für das `pub mod`; der Import bleibt bis zum
Dep-Add unauflösbar — erwartet, siehe Wellenmechanik.

- **dep-request:** `cargo add tokio-util@0.7.18 -p harw-core` (Version exakt aus `Cargo.lock`,
  `grep -n "^name = \"tokio-util\"" -A2 Cargo.lock` → `version = "0.7.18"`).
- **Feature-Nachweis:** `pub mod sync;` in `tokio-util-0.7.18` ist **ungated** (kein `#[cfg(feature = …)]`
  davor) — siehe `~/.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/tokio-util-0.7.18/src/lib.rs:57`
  (`cfg_rt!{ pub mod context; }` bei Zeile 46 ist ein anderer Block; `pub mod sync;` bei Zeile 57 steht
  ungegated danach). `cancel.rs` verwendet ausschließlich `tokio_util::sync::CancellationToken` — für
  diesen Importpfad ist **kein** Feature-Flag nötig. Empfehlung an den Orchestrator: `cargo add
  tokio-util@0.7.18 -p harw-core` **ohne** `--features`; das im Plan genannte `features = ["rt"]` ist laut
  Feature-Tabelle (`tokio-util-0.7.18/Cargo.toml:76-80`, `rt = ["tokio/rt","tokio/sync","futures-util"]`)
  nicht erforderlich für `sync::CancellationToken`, aber unschädlich, falls der Orchestrator es aus
  Konsistenzgründen dennoch setzen will (er entscheidet final per `cargo add`).
