## 1. `DefaultApprovalPolicy` trägt eine `ApprovalModeCell` (G-009)

Vorher: `#[derive(Debug, Default)] pub struct DefaultApprovalPolicy;` (Unit),
`review` las `harw_extension_api::approval_mode::current()` (lib.rs:180) —
den prozessweiten `static`, den W2A-03 parallel entfernt.

Nachher:

```rust
#[derive(Debug)]
pub struct DefaultApprovalPolicy { mode: ApprovalModeCell }

impl DefaultApprovalPolicy {
    #[must_use] pub fn new(mode: ApprovalModeCell) -> Self;
    #[must_use] pub fn requires_explicit_approval(call: &ToolCall) -> bool;  // unverändert
}
impl Default for DefaultApprovalPolicy { fn default() -> Self { Self::new(ApprovalModeCell::default()) } }
```

`review` liest `self.mode.get()` — weiterhin bei **jedem** Aufruf frisch, damit
eine Umschaltung sofort wirkt. Die drei Modus-Zweige und
`AUTO_APPROVED_TOOLS` sind unverändert (W1-05-Stand bleibt gültig).

`Default` ist **nicht** entfernt, sondern delegiert ausdrücklich an
`ApprovalModeCell::default()` (= `Delegated`, die engste Stufe ohne
Einstellung). Die Doku sagt dazu klar: Wer den Modus zur Laufzeit umschalten
können muss, darf `Default` nicht benutzen — die dort erzeugte Zelle hat
außerhalb der Politik keinen Besitzer.

`requires_explicit_approval` bleibt eine assoziierte Funktion ohne `self`;
`harw-ops/tests/approval_declaration_gate.rs` (einziger externer Nutzer) ist
davon nicht betroffen.

## 2. Montage ohne Re-Discovery (G-071, R5)

Neu in `profile.rs`, **exakte Signatur** (die vorgegebenen Typnamen existieren
alle bereits, es wurde keiner umbenannt oder neu erfunden):

```rust
pub fn assemble_registry_for_project(
    profile: RegistryProfile,
    project: &harw_project_discovery::ProjectContext,
    overrides: IdentityOverrides,
    approval_mode: harw_extension_api::approval_mode::ApprovalModeCell,
) -> RegistryDefaultsResult<AssembledRegistry>
```

- `ProjectContext` = `harw_project_discovery::{discovery::ProjectContext}`
  (`Debug + Clone`, Felder `cwd`, `project_root`, `docs`) — re-exportiert am
  Crate-Wurzel von `harw-project-discovery`.
- `IdentityOverrides` und `AssembledRegistry` unverändert übernommen
  (`profile.rs` bzw. `lib.rs`); `AssembledRegistry` hat **kein** neues Feld
  bekommen.
- Die Funktion nimmt **keinen Pfad** entgegen. Damit ist „keine zweite
  Discovery" nicht nur Verhalten, sondern durch die Signatur erzwungen — sie
  hat schlicht nichts, womit sie `discover_project` aufrufen könnte.
- `RegistryDefaultsError::ProjectDiscovery` ist hier folglich unerreichbar;
  übrig bleiben `ContextProviderRegistration` und (Feature `browser`)
  `BrowserHost`.
- `project` wird zweimal geklont (für `ProjectContextProvider` und für das
  Ergebnisfeld), nie neu ermittelt.

`assemble_registry(profile, cwd, overrides)` behält seine Signatur, führt die
Discovery **einmal** aus und delegiert danach.

**Bewusste Entscheidung — `assemble_registry` bekommt keinen 4. Parameter:**
Die Signatur ist an drei Stellen außerhalb meines Schreibbereichs verdrahtet
(`harw-cli/src/job_worker.rs:823`, `harw-cli/src/chat.rs:580`,
`harw-tui/src/app.rs:1737`) sowie indirekt über `assemble_default_registry`
(`harw-cli/src/{main.rs:690,1786,1925,2435, chat.rs:205,909,1213,
lifecycle.rs:58}`, `harw-tui/src/app.rs:1404`, `harw/examples/minimal.rs:51`,
`harw/tests/sdk_example.rs:108,179`). Sie delegiert deshalb mit
`ApprovalModeCell::default()` (`Delegated`), was dem vorherigen Startwert des
entfernten Statics entspricht. **Folge und W2c-Auftrag:** Registries aus
`assemble_registry`/`assemble_default_registry` haben eine Zelle, die niemand
außen umlegen kann — `/permissions set` in der TUI wirkt erst, wenn die
Composition-Roots ihre Sitzungs-Zelle über `assemble_registry_for_project`
durchreichen. Das ist in der Doku beider Funktionen als Folgearbeit vermerkt.
(Der prozessweite Schalter, über den das bisher lief, ist mit W2A-03 ohnehin
weg; `harw-ops/src/permissions.rs:77,123` braucht denselben W2c-Umbau.)

## 4. Tests

Kein Test benutzt noch globalen Zustand. Der Freigabemodus liegt in jeder
Testfunktion in einer **eigenen** `ApprovalModeCell`; die frühere Bündelung
„alle drei Stufen in einem Test, am Ende `Delegated` wiederherstellen"
(lib.rs:452-486, und die Parallel-Stelle in `approval_mode.rs`) entfällt
ersatzlos.

`harw-registry-defaults/src/lib.rs`:

- **entfernt** `review_reads_the_active_approval_mode_on_every_call` (mutierte
  den Prozess-Static).
- **neu** `review_in_always_ask_mode_asks_even_for_read_only_tools`,
  `review_in_delegated_mode_allows_only_the_allowlist`,
  `review_in_full_access_mode_allows_everything` — je eine eigene Zelle.
- **neu** `review_reads_the_mode_cell_on_every_call` — `cell.set(...)` auf
  einem Klon wirkt auf die bereits gebaute Politik (Zusage „sofort, nicht erst
  im nächsten Turn").
- **neu** `two_policies_with_separate_cells_do_not_influence_each_other` — der
  eigentliche Grund für G-009: Kind- und Root-Modus sind entkoppelt.
- **neu** `assembled_registry_uses_the_approval_mode_cell_it_was_given` —
  montiert über `assemble_registry_for_project` und prüft am
  `approval_handlers()[0]`, dass ein `set` auf der übergebenen Zelle die
  Registry erreicht (sonst wäre das Durchreichen wirkungslos).
- unverändert: alle Allowlist-Deckungstests aus W1-05 und
  `assemble_from_current_dir_smoke`.

`harw-registry-defaults/src/profile.rs`:

- **entfernt** `test_default_profile_is_full` (prüfte genau den Fallback, der
  jetzt weg ist).
- **neu** `test_full_is_the_only_writable_profile_and_never_a_fallback`:
  `Full` ist das einzige nicht-read-only Profil, und **keine** eingebaute Rolle
  bekommt es über `profile_for_role`. Zusammen mit dem bestehenden
  `test_profile_for_unknown_role_is_none_not_full` deckt das die fail-closed-
  Zusage ab.
- **neu** `test_assemble_registry_for_project_never_runs_discovery_again`
  (+ Helfer `make_temp_project`): legt ein Projekt unter
  `std::env::temp_dir()` mit `Cargo.toml`-Marker an (Name aus Prozess-ID +
  Nanosekunden, kein geteilter Zähler — `tempfile` ist keine Dev-Dependency
  dieses Crates, und `Cargo.toml` liegt außerhalb meines Schreibbereichs),
  entdeckt **einmal**, **löscht das Verzeichnis**, prüft ausdrücklich dass
  `discover_project` ab da scheitert, und montiert danach **zweimal**
  erfolgreich denselben Kontext. Eine verborgene Re-Discovery könnte das
  nicht — der Beweis hängt nicht an einem Zähler, sondern an der
  Unmöglichkeit. Zusätzlich geprüft: gleiche Werkzeugliste, gleicher
  `identity.cwd`, je genau ein Approval-Handler.
