### 1.2 `project_trust.rs` (neu)

`//!`-Moduldoku (Zweck, Verantwortungsabgrenzung zu `harw_home::trust`,
Nebenläufigkeit, Fehlerform, `# Examples` als ` ```ignore ` mit Begründung
„Binär-Crate, Modul nicht als Library importierbar" — Stil aus
`worker_cancellation.rs`/`main.rs::log_sensitive_enabled` übernommen, da
`harw-cli` kein `[lib]`-Target hat).

```rust
pub(crate) fn run(home_override: Option<PathBuf>, action: ProjectAction) -> Result<(), String>
fn execute(home: &Path, action: ProjectAction) -> Result<String, String>   // testbarer Kern
fn project_root(path: Option<PathBuf>) -> Result<PathBuf, String>          // DIR oder cwd
fn display_root(root: &Path) -> PathBuf                                    // Anzeige-Kanonisierung
```

- `run`: löst Home über `crate::home::resolve_home(home_override)` auf,
  ruft `execute`, druckt das Ergebnis via `println!` (User-Output, wie
  bestehender CLI-Stil — kein `tracing`-Event für die eigentliche
  Kommandoantwort; entspricht dem Muster in `auth.rs`/`chat.rs`, die
  Nutzerausgaben ebenfalls über `println!` drucken, nicht über `tracing`).
- `execute` — Fallunterscheidung:
  - `Trust{path}`: `project_root(path)` → `harw_home::trust_project(home,
    &root)` → `"trusted: <record.canonical_root> (digest <record.digest>)"`.
    `record.digest` ist bereits `blake3:<64 hex>` (siehe `trust.rs:153`),
    kein weiteres Präfix nötig.
  - `Untrust{path}`: `project_root(path)` → `harw_home::untrust_project` →
    bei `true` `"removed: <display_root>"`, bei `false` `"not trusted:
    <display_root>"`. `display_root` kanonisiert `root` eigenständig (fällt
    auf den Rohpfad zurück, falls nicht mehr auflösbar) — spiegelt exakt
    den internen Schlüssel-Fallback aus `untrust_project` (trust.rs:402-407),
    da die Funktion selbst nur `bool` zurückgibt und keinen Pfad.
  - `Status{path}`: `project_root(path)` → `harw_home::project_trust_status`
    → Label `Trusted`/`Untrusted`/`Changed` (exhaustives `match` auf
    `harw_home::TrustStatus`) + `display_root` (gleiche Kanonisierung wie
    oben) → `"<Label>: <root>"`.
- Fehler: jeder `HomeError`/IO-Fehler wird mit `format!("… fehlgeschlagen
  für {}: {error}", root.display())` in Kontext gesetzt (Pfad + Ursache),
  kein stilles Verwerfen, kein `unwrap()`/`expect()` im Produktionspfad.
- Kanonisierung: **nicht** selbst dupliziert — `trust_project`,
  `untrust_project`, `project_trust_status` kanonisieren `root` intern
  (`canonical_project_root`, trust.rs:546, nutzt `std::fs::canonicalize`);
  `project_trust.rs` reicht den Roh-Pfad (DIR oder `cwd`) unverändert
  durch. `display_root` (nur für die Nutzerausgabe bei Untrust/Status)
  kanonisiert zusätzlich lokal mit derselben `std::fs::canonicalize`-Logik,
  weil `untrust_project`/`project_trust_status` den kanonischen Pfad nicht
  zurückgeben.

### Tests (`project_trust.rs`)

- `test_run_trust_then_status_reports_trusted`: Temp-Home
  (`tempfile::tempdir` + `harw_home::ensure_home`), Temp-Projekt mit

  nutzen, die den Ausgabetext zurückgibt"), keine Prozessumgebung
  (`set_var`/`set_current_dir`) verändert, nur Tempdirs.

## 2. Neuer Pattern-Shape für M1a (main.rs-Dispatch)

`main.rs` selbst wurde **nicht** geändert (Owned files dieses Agents
enthalten `main.rs` nicht). Für M1a exakt die zwei nötigen Anpassungen:

1. **`mod project_trust;`** in der Modulliste ergänzen (alphabetisch nach
   `mod onboarding;`, vor `mod resume;` — siehe bestehende Sortierung
   `main.rs:16-35`).
2. **Dispatch-Arm** für `Command::Project` ergänzen, analog zu den
   bestehenden `Some(Command::…) => { … }`-Armen (`main.rs` um Zeile
   239-260):

   ```rust
   Some(Command::Project { action }) => {
       project_trust::run(home_override, action)?;
   }
   ```

   `home_override` ist dieselbe Bindung, die auch an `Command::Doctor`/
   `Command::Serve`/`Command::Web` in den bestehenden Armen übergeben wird
   (`main.rs:239-252`, dort als erstes Argument von `resolve_layers`/
   `resolve_serve_paths`). `project_trust::run` ist `pub(crate)` und
   konsumiert `home_override: Option<PathBuf>` direkt — keine
   Vorauflösung durch `main.rs` nötig, `run` löst intern über
   `crate::home::resolve_home` auf.

3. **`Command::Web`-Aufrufstellen** (`main.rs:248-260`,
   `main.rs:307-310`) müssen den entfernten `config_dir`-Feldbinder
   entfernen — das ist zusammen mit W1s `serve_web`-Signaturänderung
   (siehe `ledger/W2d2/W1.md` §2) zu erledigen, da beide Änderungen an
   derselben `main.rs`-Stelle zusammentreffen:
   - **Bisher**: `Some(Command::Web { config_dir, socket }) => { … }` und
     `Some(Command::Web { config_dir, .. })` im `match config_dir { … }`
     weiter unten (`main.rs:309-310`).
   - **Neu**: `Some(Command::Web { socket }) => { … }` — der
     `config_dir`-Bindung entfällt vollständig; die Verzweigung
     `main.rs:307-310`, die bislang `Command::Doctor`/`Command::Serve`/
     `Command::Web` gemeinsam auf `config_dir` matcht, muss `Command::Web`
     aus diesem gemeinsamen Arm herauslösen (nur noch `Doctor`/`Serve`
     bleiben dort, da nur diese beiden weiterhin `config_dir` führen).
   - Bis M1a diese Anpassung vornimmt, kompiliert `main.rs` nicht mehr
     gegen `cli.rs::Command::Web` (erwartete, temporäre Inkonsistenz
     zwischen M2/W1 und M1a — laut CONTRACTS-W2d2.md Stufe 4 aufgelöst).

## 6. Annahmen

- `record.digest` (Form `blake3:<64 Hex>`) wird unverändert in der
  Trust-Ausgabe angezeigt, ohne zusätzliches Präfix — abgeleitet aus dem

  kanonischen Pfad zurückgeben — funktional deckungsgleich mit dem intern
  von `harw_home::trust` verwendeten Schlüssel.
