## 2. Signatur (wie geschrieben)

```rust
fn runtime_composition_evidence(
    home: &Path,
) -> Result<harw_install::doctor::RuntimeCompositionEvidence, String> {
    let cwd = std::env::current_dir().map_err(|error| format!("cwd: {error}"))?;
    let assembly = crate::runtime_entry::doctor_assembly(home, &cwd)?;
    let rights = assembly.rights_snapshot();
    let has_trusted_spawn_context = assembly.spawn_context().approval_actor.is_some();
    let has_approval_boundary = !rights.approval_chain.is_empty();

    Ok(harw_install::doctor::RuntimeCompositionEvidence {
        advertised_tools: Some(rights.tools),
        has_trusted_spawn_context: Some(has_trusted_spawn_context),
        has_approval_boundary: Some(has_approval_boundary),
    })
}
```

Geändert gegenüber der Vorgabe im Brief: die Signatur nimmt jetzt `home: &Path` entgegen (statt keiner
Parameter); `cwd` bleibt intern über `std::env::current_dir()` mit Fehler-Mapping `"cwd: {error}"` aufgelöst
— wortgleich zur bisherigen Zeile, nur nicht mehr die einzige externe Eingabe. `health_checks(home: &Path)`
reicht `home` jetzt durch (`runtime_composition_evidence(home)?`), statt es nur für die
`HomeExistsCheck`/`HomePermsCheck`-Paare zu nutzen.

## 6. Bekannte Einschränkung — kein Bau ausgeführt

Wie bei allen W2d-2-Knoten: **nur gelesen, nicht gebaut/getestet** (BUILD-POLICY). Die Korrektheit von
`rights.tools`/`rights.approval_chain`/`spawn_context().approval_actor` gegen ein leeres Temp-Home stützt
sich auf E1s bereits durch Lesen verifizierten `test_doctor_assembly_succeeds_with_empty_home` (derselbe
Aufbau: leeres Temp-Home, reales `cwd` des Testprozesses) sowie auf die zitierten Doku-Kommentare in
`assembly.rs`/`spec.rs`. Der genaue Werkzeug-Mengeninhalt (`base` vs. `with_browser`) wird erst durch den
Orchestrator-Bau in Stufe 4 verifiziert; sollte `doctor_assembly`s Full-Profil-Montage eine andere
Werkzeugmenge als die bisherige `assemble_default_registry(cwd)`-Montage ergeben, schlägt der Test sichtbar
fehl statt still durchzurutschen.
