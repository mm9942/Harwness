## Ablauf `run_tui`

1. `current_thread`-Runtime.
2. `build_root_runtime`: `TuiApprovalHandler::new()` → `ApprovalDriver::new(Arc::clone)`; Turn-Kanal;
   `assembly.new_root_session(root_session_id.clone(), wiring.events_tx, turn_tx, Some(as_dyn_approval_handler(&h)))`
   (RuntimeError → `TuiError::Core("could not build the root session: …")`); Adapter aus
   `assembly.operations()`; `ChatApp::with_memory(adapters, sandbox.clone(), id, memory().cloned())
   .with_runtime(Arc::clone).with_session_controller(wiring.controller).with_project_root(project().project_root.display())
   .with_managed_spawner(spawner().cloned())`, ggf. `.with_plan_services((plan).into())`; `set_active_mode(session.mode())`.
   Modus-Override setzt die Montage selbst (`spec.mode_override` in `new_root_session`).
3. Verlauf aus `assembly.state_store()` laden (Fehler fatal wie bisher), `install_loaded_history`, WELCOME.
4. `ResumableGateway::new(session, state_store, model)`, `TerminalGuard::enter`, Schleife wie alt app.rs:2231-2338.
   - `Resume{None}`: mit TuiResume → Liste/leer/Fehlertext; ohne → „Session resume is not configured.“
   - `Resume{Some}`: ohne TuiResume → Hinweis; sonst `resolve_session` → `factory.assemble(Some(id))`
     → `build_root_runtime` → Verlauf laden + WELCOME → `gateway.replace(session, store, model)`, App/Kanäle/Treiber
     tauschen → `old.close_session(old.root_session_id())`.
   - `Quit` → Ok.
5. Guard droppen, dann `current.close_session(current.root_session_id())`.

## Annahmen / Hinweise an Orchestrator

1. **Resume-Fehler nicht fatal** (Abweichung zur alten Schleife, wo `build_session_runtime` per `?` beendete):
   Auflösen, Montage (`String`), `build_root_runtime` und Verlaufsladen der neuen Sitzung erzeugen eine
   Systemzeile; die laufende Sitzung bleibt aktiv. Scheitert nur das Verlaufsladen, wird die bereits erzeugte
   neue Wurzelsitzung per `close_session` gemeldet.
2. **close_session auch bei Fehlerausgang** der Schleife (nicht nur Quit): die aktive Sitzung endet in beiden Fällen.
3. **`as_dyn_approval_handler` liegt jetzt in runtime_root.rs (`pub(crate)`).** app.rs-Tests im tabu-Bereich
   (heute app.rs:4287, :4408, `approval_arming_tests`) rufen es unqualifiziert; T2a muss es in app.rs
   importieren (`use crate::runtime_root::as_dyn_approval_handler;`, ggf. `#[cfg(test)]`), sonst bricht der Test-Build.
4. `TuiApprovalHandler` überschreibt `label`/`kind` nicht (Vorgabe `"unnamed"`/`Other`); der Responder-Test
   vergleicht deshalb gegen die Trait-Methoden des Handlers statt gegen Literale.
5. Systemtexte werden über `push_lines` (eine Zeile je Textzeile) statt `push_line(Role::System, …)` angehängt,
   weil §1.2 nur `push_lines` zusagt; Darstellung gleichwertig (`PlainHistoryCell`).
6. Doctests `no_run` im Modul (`run_tui`, `TuiSessionWiring::{new, install}`) werden kompiliert; sie setzen
   `RuntimeError: std::error::Error` (HarwError-Derive) voraus.
7. `ChatApp::with_memory` öffnet `InputHistoryStore` über `harw_home::paths::home_dir` (nur Lesen) — wie
   bestehende app.rs-Tests.
8. Nicht gebaut: `cargo test -p harw-tui runtime_root`, clippy `-D warnings`, rustfmt durch Orchestrator.
