## R2-11 – `harw-tool-web/src/fetch.rs`

`validate_target` (`fetch.rs:318` vorher) prüfte das Schema per
String-Präfix (`trimmed.get(..8).is_some_and(|p| p.eq_ignore_ascii_case
("https://"))`) und reichte den Rest an `harw_tools::host_from_url` weiter —
doppelte Wahrheit ggü. `EgressUrl::parse`, das `reqwest` beim
Verbindungsaufbau intern ebenfalls über `url::Url` nutzt.

Fix: `validate_target` ruft jetzt `EgressUrl::parse(trimmed)` auf und bildet
Fehler auf die bestehenden `WebToolError`-Varianten ab (keine neuen
öffentlichen Typen, Signatur `fn(&str) -> WebToolResult<String>` unverändert):

- `EgressUrlError::UnsupportedScheme(_)` → `WebToolError::SchemeNotAllowed`
  (deckt `ftp://`, `file://`, `data:`, jedes Nicht-http(s)-Schema).
- `EgressUrlError::{Parse, UserinfoPresent, MissingHost, InvalidHost}` →
  `WebToolError::HostNotResolvable` (kein Host extrahierbar/verwendbar).
- Nach erfolgreichem Parse zusätzlich `!parsed.is_https()` →
  `WebToolError::SchemeNotAllowed`, weil `EgressUrl::parse` sowohl `http` als
  auch `https` akzeptiert (Vertrag §egress), diese Funktion aber nur
  `https://` zulassen darf — deckt `http://docs.rs/…`.
- Erfolgsfall: `Ok(parsed.host_str())`.

Import ergänzt: `use harw_sandbox::{EgressUrl, EgressUrlError, NetworkScope};`
(vorher nur `NetworkScope`; Stil wie `harw-tools/src/sandbox_guard.rs:42`,
das dieselben Typen bereits so importiert). Rustdoc von `validate_target`
(`fetch.rs:289-317`) aktualisiert: „Userinfo wird abgelehnt“ statt „ohne Port
und Userinfo“ (R2-01-Zusatzauftrag „Doku Z. 302“).

Alle neun bestehenden `validate_target`-Tests (http-Schema, andere Schemata,
Großschreibung, fehlender Host) wurden gegen die neue Implementierung
durchgerechnet und bleiben grün; keiner mit Ausnahme des unter R2-01
behandelten Falls war auf die alte String-Präfix-Logik angewiesen.

## R2-01 – Test aufgeteilt

`test_validate_target_strips_port_and_userinfo` (`fetch.rs:1549-1555` vorher)
erwartete `validate_target("https://user:pw@Docs.RS:8443/x") ==
Ok("docs.rs")`. Mit `EgressUrl::parse` liefert dieselbe URL
`Err(EgressUrlError::UserinfoPresent)` → `WebToolError::HostNotResolvable`
(Verhaltensänderung ist beabsichtigt, siehe `W0B-04.md` §5 und
`review-Z0-R2.md` R2-01). Aufgeteilt in zwei Tests:

- `test_validate_target_strips_port_and_lowercases`: `"https://Docs.RS:8443/x"`
  (ohne Userinfo) → `Ok("docs.rs")` — Port- und Case-Verhalten bleibt geprüft.
- `test_validate_target_rejects_userinfo`: `"https://user:pw@Docs.RS:8443/x"`
  → `Err(WebToolError::HostNotResolvable { .. })` — exakte Fehlervariante
  belegt durch die Fehlerabbildung in `validate_target` selbst (siehe oben);
  `EgressUrlError::UserinfoPresent` ist in dieser Abbildung Teil des
  `HostNotResolvable`-Zweigs, nicht `SchemeNotAllowed`.

## R2-02 – `harw-dod-netpolicy/src/rule.rs`

`host_matches` (`rule.rs:163-178` vorher) war eine Handkopie der
Punktgrenzen-Regel, die laut eigenem Kommentar „identische Semantik zu
harw_sandbox's `host_matches`“ beanspruchte, aber keinen abschließenden Punkt
tolerierte (`docs.rs.` gegen `AllowDnsSuffix("docs.rs")` schlug fehl, während
`harw_sandbox::NetworkScope::allows` das seit W0B-04 zulässt).

Fix: `host_matches` delegiert jetzt an `harw_sandbox::host_matches_suffix`
(`rule.rs:165-167`):

```rust
fn host_matches(allowed: &str, needle: &str) -> bool {
    harw_sandbox::host_matches_suffix(allowed, needle)
}
```

`harw_sandbox` war in der Datei bereits importiert (`use
harw_sandbox::EgressTarget;`, `rule.rs:17`); der Aufruf nutzt den vollen Pfad
`harw_sandbox::host_matches_suffix`, kein zusätzlicher `use`-Eintrag nötig.
`harw-dod-netpolicy/Cargo.toml:8` hängt bereits an `harw-sandbox` — keine
Manifest-Änderung.

Dokumentation angepasst: Der Kommentar über `host_matches` (`rule.rs:157-164`)
verweist jetzt auf die Delegation statt „identische Semantik“ zu behaupten;
der Rustdoc-Absatz über `allows_host` (`rule.rs:100-108` vorher) strich den
inzwischen falschen Satz „`harw-sandbox` exportiert diese
Vergleichsfunktionen nicht öffentlich“.

Test ergänzt: `test_allow_dns_suffix_rule_tolerates_one_trailing_dot` prüft
beide Richtungen (`allowed` mit/ohne abschließenden Punkt, `needle` mit/ohne)
gegen `AllowDnsSuffix`. Bestehende Tests (`test_allow_dns_suffix_rule_matches
_at_a_dot_boundary`, `test_allow_host_rule_matches_only_the_exact_name`,
`test_allow_cidr_rule_matches_only_addresses_never_hosts`,
`test_normalize_host_trims_case_and_leading_dot`) unverändert grün, da
`host_matches_suffix` für alle bisher geprüften Fälle (exakter Treffer,
Punktgrenzen-Suffix, leerer Eintrag, Nicht-Suffix) dasselbe Ergebnis liefert
wie die vorherige Handkopie — der einzige Verhaltensunterschied ist die neue
Trailing-Dot-Toleranz.
