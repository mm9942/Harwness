## Verhaltensänderungen

1. `CryptoPolicy::strongest()`/`Default` = hybrides ML-KEM-1024/P-384 + XChaCha20-Poly1305 (vorher reines ML-KEM-1024).
2. Aus demselben 32-Byte-KEK-Seed entsteht ein **anderer** Public Key als früher; der Seed selbst bleibt gültig.
3. **Legacy-Envelopes unlesbar:** Datensätze mit `kem_algo` `ml_kem_512`/`ml_kem_768`/`ml_kem_1024`
   laden noch in den Index (`SecretStore::open*`, `list`, `metadata`, `record`), aber `get`, `get_by_reference`,
   `envelope::open` und `rewrap_v2`/`SecretStore::rotate` liefern `SecretsError::UnsupportedLegacyKem { algo }`.
   Eine Rotation bricht ab, sobald ein Legacy-Datensatz existiert (ohne Platten-/Speicheränderung).
4. `seal` mit Legacy-Policy → `UnsupportedLegacyKem` (vor jeder Kryptoarbeit); der Public Key wird jetzt vor
   der DEK-Erzeugung validiert.
5. Legacy-`KemAlgo`-Varianten sind nicht serialisierbar (`serde` liefert Fehler) – kein neues Artefakt kann
   einen reinen ML-KEM-Namen tragen.
6. `derive_secret_key` liefert für Hybrid-KEMs den 32-Byte-Seed (vorher 64-Byte-ML-KEM-Seedformat);
   `derive_public_key`/`derive_secret_key` liefern `UnsupportedLegacyKem` für Legacy-Policies.
7. `kek::validated_seed` kopiert den Seed nicht mehr in ein nicht-löschendes Stack-Array.
8. Text von `SecretsError::KekDerivation` lautet jetzt „…KEK-to-hybrid-ML-KEM…“ (kein Test/Aufrufer hängt am Text).

## Offene Annahmen / Compile-Risiken

- **Nicht kompiliert, nicht getestet, nicht formatiert** (Verbot bzw. rustfmt fehlt). Formatierung von Hand im
  Stil des Bestands (u. a. Import-Sortierung wie vorhandener Code, nicht style_edition 2024); `cargo fmt --check`
  kann Abweichungen melden.
- `#[serde(rename = "...", skip_serializing)]` auf Unit-Varianten: laut serde_derive-Quelle unterstützt (siehe Nachweis).
- Typinferenz `expose_secret().as_ref()` auf `&Box<[u8]>` in Tests entspricht dem bisherigen Muster.
- `validated_seed`: Deref-Koerzierung `&Box<[u8]>` → `&[u8]` über explizite Typannotation.
- P-384-Skalar aus 48 Byte SHAKE-Ausgabe kann theoretisch (≈2^-190) ungültig sein → `KekDerivation`
  (`M:2278-2279`); praktisch irrelevant, aber kein Retry in crypt_guard.
- Hybrid + SHAKE256 + private AEADs ist in crypt_guard 3.0.1 nicht durch eigene Tests abgedeckt
  (dortige Hybrid-Tests nutzen HKDF + Standard-AEADs, `C/tests/pq05_hybrid_p384.rs:45-60`,
  `C/tests/pq05_hybrid_x25519.rs:65-80`); Codepfad laut Quelle KEM-unabhängig – unsere Roundtrip-Tests decken ihn ab.
- `SecretStore::delete`-Rollback bei Audit-Fehler (`store.rs` `persist_secret` nach Löschung) kann einen
  Legacy-Datensatz nicht zurückschreiben (Serialisierung verweigert) – der Fehler wird dort bereits bewusst
  verworfen; betrifft nur ohnehin unlesbare Legacy-Datensätze.
