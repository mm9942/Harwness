## Befund R3-04 – behoben

`clippy::type_complexity` (Standard-Warnung, Schwelle 250) griff bei zwei
`let`-Typannotationen mit rohen Tupel-Array-Typen in den Testmodulen:

- `harw-runtime/src/spec.rs:340` (vorher):
  `let expected: [(EntryKind, &[Permission], P, O, A, S, C); 11] = [...]`
- `harw-runtime/src/error.rs:55` (vorher):
  `let cases: [(fn(String) -> RuntimeError, &str); 8] = [...]`

### Fix

**`spec.rs`** (Testmodul, vor `profile_matches_contract_table`): Typalias
`Row` eingeführt, exakt derselbe Tupeltyp wie vorher, nur benannt:

```rust
type Row = (
    EntryKind,
    &'static [Permission],
    RegistryProfile,
    OperationSurface,
    AskResolution,
    SpawnerPolicy,
    CeilingPolicy,
);
```

`let expected: [(EntryKind, &[Permission], P, O, A, S, C); 11]` →
`let expected: [Row; 11]`. Die vorherige (nicht lebenszeit-annotierte)
`&[Permission]`-Slice-Referenz in der Inline-Signatur war implizit an
`'static` gebunden (alle Einträge sind `&[R, W, X]`-artige Literale); der
Alias macht das jetzt explizit (`&'static [Permission]`) — reine
Namensgebung, keine Typänderung, keine Semantikänderung.

**`error.rs`** (Testmodul, vor `display_names_phase_and_detail`): Typalias
`Make` eingeführt:

```rust
type Make = fn(String) -> RuntimeError;
```

`let cases: [(fn(String) -> RuntimeError, &str); 8]` → `let cases: [(Make, &str); 8]`.
Identischer Funktionszeigertyp, nur benannt.

Beide Aliase sind `type`-Items innerhalb des jeweiligen `#[cfg(test)] mod
tests`-Blocks, nicht öffentlich, ändern keine öffentliche Signatur und keine
Laufzeit-Semantik. Die Werte-Arrays selbst (`expected`, `cases`) sind
unverändert; nur die Typannotation ist jetzt ein Alias statt eines
ausgeschriebenen Tupeltyps.
