## Befund

Sechs Dateien hatten je zwei hartkodierte `O_NOFOLLOW`-Konstanten
(`0o400000` für `target_os = "linux"/"android"`, `0x100` für die übrigen
gelisteten Unix-Ziele) und reichten sie über
`std::os::unix::fs::OpenOptionsExt::custom_flags` an `OpenOptions::open`
weiter. `0o400000` ist auf aarch64-Linux tatsächlich `O_LARGEFILE`
(harmloses Flag) statt `O_NOFOLLOW` (dort `0o100000`) — auf dem
Ziel-Raspberry-Pi (aarch64) wirkte der Symlink-Schutz an diesen Stellen also
**nicht**. Zusätzlich folgte `ApprovalStore::lock_session`
(`harw-session-store/src/approval.rs`) Symlinks komplett: kein
`custom_flags`-Aufruf, keine Vorab-Prüfung.

## Änderungen

Alle sechs Fundstellen (verifiziert per `grep -rn "O_NOFOLLOW\|custom_flags"`,
keine weiteren im Workspace außerhalb `harw-fsutil/`) ersetzen die Konstante
und den `custom_flags`-Aufruf durch `harw_fsutil::open_nofollow(path, OpenMode
{ .. })`. Mode-Felder sind bitgenau aus den vorherigen `OpenOptions`-Aufrufen
übernommen (siehe Tabelle); `mode: 0o666` entspricht dem `std::fs::OpenOptions`-
Default ohne `.mode(...)`-Aufruf (kein `.mode()` stand vorher irgendwo). Auf
Nicht-Unix (`#[cfg(not(unix))]`) bleibt die alte `OpenOptions`-Fassung ohne
`O_NOFOLLOW` erhalten — identisch zum bisherigen Verhalten dort (die
`custom_flags`-Aufrufe waren zuvor über eine `target_os`-Liste ohnehin nur auf
Unix wirksam; `harw-fsutil` selbst ist unix-only, `#[cfg(unix)]` ist eine
oberflächengleiche, aber wartbarere Fassung derselben Liste).

### `harw-session-store/src/approval.rs::lock_session` — separater Bug

Diese Funktion hatte **kein** `custom_flags` und keine Symlink-Vorprüfung
(„ApprovalStore folgt Symlinks sogar ganz“, Auftragstext). Neue Funktion
`open_lock_file_without_following_symlinks` kapselt jetzt
`harw_fsutil::open_nofollow` mit denselben Flags wie vorher
(`create+truncate(false)+read+write`, Default-Mode `0o666`). Das ist eine
echte Verhaltensänderung (siehe unten), nicht nur ein Konstantentausch.

### `read_pending` (approval.rs) — Vereinheitlichung auf `#[cfg(unix)]`

Vorher: `#[cfg(any(linux, android))]` nutzte die (falsche) `O_NOFOLLOW`-Zahl;
alle anderen Unix-Ziele (macOS, *BSD, illumos, solaris) verließen sich **nur**
auf eine TOCTOU-anfällige `symlink_metadata`-Vorabprüfung ohne echtes
`O_NOFOLLOW` beim Öffnen (Kommentar im Alt-Code: „Other Unix targets use the
metadata check in the fallback below“). Da `harw_fsutil::open_nofollow` auf
jedem Unix-Ziel korrekt ist (das ist der Zweck des Crates), habe ich
`read_pending` auf ein einziges `#[cfg(unix)]` vereinheitlicht — das schließt
die TOCTOU-Lücke auf den vorher schwächer geschützten Zielen zusätzlich. Der
ELOOP→NotFound-Remap lief vorher über den plattformspezifischen Errno-Zahlwert
40 (nur auf Linux/Android korrekt); jetzt über
`std::io::ErrorKind::FilesystemLoop` (stabil seit Rust 1.83, MSRV hier 1.85),
was auf jeder Unix-Plattform korrekt ist, weil `rustix`s
`From<Errno> for io::Error` (`rustix-1.1.4/src/io/errno.rs:58`) über
`Error::from_raw_os_error` läuft und damit std’s eigene, plattformkorrekte
Errno→ErrorKind-Tabelle nutzt.

### `harw-secrets/src/kek.rs` — cfg-Gate bewusst NICHT erweitert

`check_key_file_permissions`/`open_key_file`/`load_key_file_seed` bleiben
`#[cfg(any(target_os = "linux", target_os = "android"))]`-gated (unverändert).
Der Code dokumentiert explizit ein bewusstes Fail-Closed auf allen anderen
Zielen („requires verified no-follow and permission validation“) — das ist
eine Plattform-Vertrauensentscheidung außerhalb dieses Tickets (F-006 betrifft
nur die falsche Konstante). Innerhalb des bestehenden Gates wurde nur die
Konstante durch `harw_fsutil::open_nofollow` ersetzt.

## API-Nachweise (harw-fsutil, bereits in W0B-03/Z0-F4 belegt, hier nur zitiert)

- `harw-fsutil/src/open.rs:60-137` `OpenMode` (Felder `read,write,create,
  create_new,truncate,append,mode`) + Konstruktoren `read_only`,
  `write_truncate`, `append_create` — exakt wie im Crate implementiert.
- `harw-fsutil/src/open.rs:254-259` `pub fn open_nofollow(path: &Path, mode:
  OpenMode) -> io::Result<File>`.
- `harw-fsutil/src/lib.rs:513` Re-Export `pub use open::{OpenMode, ...,
  open_nofollow};` auf Crate-Ebene.
- `harw-fsutil/src/open.rs:407-427` `finish_open`: öffnet mit `O_NONBLOCK`,
  lässt nur `RegularFile`/`Directory` passieren (sonst `InvalidInput`),
  entfernt `O_NONBLOCK` danach wieder — für alle sechs Aufrufstellen ohne
  Wirkung geprüft: es wird nirgends ein Verzeichnis oder eine Nicht-Datei über
  diese Pfade geöffnet (Session-Locks, Transcript-/Job-/Approval-/Signal-
  Dateien, KEK-Key-Datei sind immer reguläre Dateien). `open_dir_nofollow`
  war an keiner der sechs Stellen nötig.

## Verhaltensänderungen

1. **Sicherheitsfix (Kernauftrag):** Auf aarch64 (Ziel-Raspberry-Pi) wirkte
   der Symlink-Schutz an allen sechs Stellen vorher **nicht** (`0o400000` =
   `O_LARGEFILE`, kein `O_NOFOLLOW`); jetzt korrekt über
   `rustix::fs::OFlags::NOFOLLOW`.
2. `ApprovalStore::lock_session` folgte vorher Symlinks vollständig (kein
   Schutz); folgt jetzt keinem Symlink mehr im letzten Pfadglied. Neuer
   Regressionstest `symlinked_session_lock_is_rejected_without_opening_its_target`
   zeigt den alten Fehler (vorher hätte der Test mit der alten
   Implementierung fehlgeschlagen: die externe Datei wäre geöffnet und
   gelockt worden).
3. `approval.rs::read_pending` schützt jetzt auch macOS/*BSD/illumos/solaris
   über echtes `O_NOFOLLOW` statt nur TOCTOU-anfälliger Metadaten-Prüfung
   (vorher nur Linux/Android geschützt).
4. `harw-secrets::kek::open_key_file`: Für eine FIFO/ein Gerät an der
   Zielposition liefert `harw_fsutil::open_nofollow` jetzt vor jeder
   Validierung `InvalidInput` (`SecretsError::Io`) statt vorher potenziell
   blockierend zu öffnen und erst danach über `validate_key_file`s
   `is_file()`-Prüfung mit `SecretsError::KekUnavailable{kind:"key-file",...}`
   abzulehnen. Fehlerklasse ändert sich für diesen (ungetesteten) Randfall;
   Erfolgs-/Symlink-/Permission-Fälle bleiben identisch (bestehender Test
   `key_file_rejects_a_symlink_instead_of_following_it` prüft nur
   `SecretsError::Io(_)`, unverändert grün).
5. Alle übrigen Stellen (store.rs, reader.rs, job_store.rs, file_store.rs):
   sichtbares Verhalten unverändert (bereits vorhandene
   `symlink_metadata`-Vorabprüfungen fangen die in den Tests konstruierten
   Symlink-Fälle weiterhin identisch ab); die Korrektur schließt dort die
   TOCTOU-Lücke zwischen Vorabprüfung und tatsächlichem `open()` sowie den
   architekturabhängigen Bug im `open()` selbst.
