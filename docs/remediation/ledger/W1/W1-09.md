## Befund (G-051)

`input_editor.rs::handle_key` behandelte `KeyCode::Enter` bei nicht-leerem Puffer
immer als `Submit`, unabhängig davon, wie das Enter-Ereignis entstand. Liefert das
Terminal Bracketed Paste nicht (verhandelt `CSI ?2004h` nicht, alte/exotische
Terminals, tmux-Fehlkonfiguration), kommt ein Copy-Paste stattdessen als schneller
Strom einzelner `KeyCode::Char`/`KeyCode::Enter`-Ereignisse an. Jedes eingefügte
`\n` traf dadurch auf den normalen Enter-Zweig: der bis dahin aufgelaufene
Teilpuffer wurde sofort abgesendet und über `classify_input` (`input.rs:17-33`)
klassifiziert — begann eine Paste-Zeile mit `/` oder `!`, wurde sie automatisch als
Slash-/Shell-Befehl ausgeführt, ohne dass der Nutzer je bewusst Enter für genau
diese Zeile gedrückt hat. `Event::Paste` (echtes Bracketed Paste, verarbeitet in
`app.rs`, außerhalb dieses Dateibereichs) war davon nicht betroffen — dieses
Register betraf ausschließlich den Fallback-Pfad ohne Bracketed Paste.

## Geänderte Datei

`harw-tui/src/input_editor.rs` (einzige erlaubte Schreib-Datei dieser Welle):

1. **`PasteBurstDetector`** (neuer, privater Typ, `Debug + Clone + Default`):
   reine Zustandsmaschine ohne Bezug zum Editor-Puffer. `observe(&mut self, now:
   Instant) -> bool` bekommt für jedes Zeichen-/Enter-Ereignis einen injizierten
   Zeitstempel und meldet, ob ab diesem Ereignis ein Burst als aktiv gilt.
   Keine `Instant::now()`-Aufrufe im internen Zustand → deterministisch testbar.
2. Konstanten `PASTE_BURST_INTERVAL = Duration::from_millis(8)` und
   `PASTE_BURST_MIN_EVENTS: u32 = 3` (Schwellwerte exakt wie in der Aufgabe
   vorgegeben: „< 8 ms zwischen Ereignissen über ≥ 3 Zeichen“).
3. Neues Feld `InputEditor::paste_burst: PasteBurstDetector`, initialisiert in
   `with_capacity` über `PasteBurstDetector::default()`.
4. `InputEditor::handle_key` wurde zu einem dünnen Wrapper:
   `handle_key(&mut self, key) -> InputAction { self.handle_key_at(key,
   Instant::now()) }`. Die gesamte bisherige Logik steckt jetzt in der neuen
   `pub fn handle_key_at(&mut self, key: KeyEvent, now: Instant) -> InputAction`
   — Signatur von `handle_key` bleibt unverändert (kein Bruch für Aufrufer wie
   `app.rs`, das nicht Teil dieser Welle ist), `handle_key_at` ist die
   Zeitquellen-injizierbare Variante für Tests.
5. Im `KeyCode::Char(ch) if !ctrl`-Zweig: `self.paste_burst.observe(now)` vor
   `insert_char` (jedes druckbare Zeichen zählt für die Burst-Erkennung).
6. Im `KeyCode::Enter`-Zweig (ohne Shift, ohne `Ctrl+J` — die bleiben unverändert
   immer „Zeilenumbruch einfügen“): zuerst `self.paste_burst.observe(now)`
   aufrufen; liefert das `true` (Burst aktiv), wird nur `insert_newline()`
   ausgeführt und `Redraw` zurückgegeben — **kein** `Submit`, unabhängig vom
   Pufferinhalt. Erst wenn `observe` `false` liefert (Ruhephase ≥ 8 ms seit dem
   letzten Zeichen-/Enter-Ereignis, oder gar kein vorheriges Ereignis), läuft
   die alte Submit-Logik (leer → `Passthrough`, sonst `Submit` + `clear`).
7. Dokumentationskommentare (Modul-Kopf, Typ-Doku, `handle_key_at`-Tabelle)
   erklären Bedrohungsmodell und Verhalten auf Deutsch.

`Event::Paste` (Requirement 2) wird von diesem Modul nicht direkt konsumiert
(`app.rs` ruft weiterhin `insert_str` auf den ganzen Block, ohne über
`handle_key`/`handle_key_at` zu gehen) — daran wurde nichts verändert, das bleibt
also weiterhin ein atomarer Block, unbeeinflusst vom neuen Burst-State.

## API-Nachweise

- `crossterm 0.29.0` (`Cargo.lock:3293`, `Cargo.toml:8` in `harw-tui`) —
  `KeyCode`, `KeyEvent`, `KeyModifiers` unverändert gegenüber dem bereits im
  Bestand genutzten Import (`input_editor.rs:32`, keine Signaturänderung an
  crossterm-Typen nötig, da nur Zeitstempel *zusätzlich* zum bestehenden
  `KeyEvent`-Parameter durchgereicht werden).
- `std::time::Instant`/`Duration`: `Instant + Duration -> Instant`
  (`impl Add<Duration> for Instant`), `Instant::duration_since` sättigt seit
  Rust 1.60 bei `now < prev` auf `Duration::ZERO` (kein Panic) — MSRV dieses
  Workspace ist 1.85, damit unproblematisch.
- `Option::is_some_and` stabilisiert seit Rust 1.70 — MSRV 1.85 erfüllt.

## Tests (alle neu, `#[cfg(test)] mod tests` in derselben Datei)

25. `test_paste_burst_detector_activates_after_min_events` — reine
    `PasteBurstDetector`-Logik: 1./2. Ereignis (1 ms Abstand) noch nicht aktiv,
    3. Ereignis aktiviert den Burst.
26. `test_paste_burst_detector_quiet_gap_resets` — ein 50-ms-Abstand nach
    aktivem Burst deaktiviert ihn beim nächsten Ereignis sofort wieder.
27. `test_paste_burst_multiline_slash_bang_stays_in_buffer` — Kernszenario aus
    der Aufgabe: `"/quit\n!rm -rf x\n"` Zeichen für Zeichen mit 1-ms-Abstand über
    `handle_key_at` eingespeist; kein einziges Ereignis liefert `Submit`, der
    komplette Text (inkl. beider `\n`) bleibt im Puffer.
28. `test_normal_typing_with_slow_enter_submits` — Gegenprobe: „hallo“ mit
    50-ms-Abständen getippt, abschließendes Enter (ebenfalls 50 ms später)
    liefert weiterhin `Submit("hallo")` — normales Tippen unbeeinträchtigt.
29. `test_paste_event_with_slash_command_does_not_auto_submit` — simuliert den
    Bracketed-Paste-Pfad über `insert_str("/cmd\n!echo hi\n")` (wie `app.rs` es
    für `Event::Paste` tut): kein automatisches Absenden; erst ein danach
    bewusst gedrücktes Enter (normaler Abstand, kein vorheriges Burst-Ereignis)
    sendet den kompletten Block als eine Einheit ab.

Bestehende 26 Tests unverändert; da `PasteBurstDetector` pro `InputEditor::new()`
frisch mit `last_event_at: None` startet, verhält sich das allererste
`handle_key`/`handle_key_at`-Enter-Ereignis in jedem bestehenden Test weiterhin
wie zuvor (`observe` liefert beim ersten Aufruf immer `false`, siehe
`test_handle_key_enter_submits`, `input_editor.rs`).

  `\n` in `"/quit\n!rm -rf x\n"` landen damit sicher im `insert_newline`-Zweig.
