## 4. `check_approval` — Aggregation (`harw-core/src/turn_loop.rs:490`)

Vorher (gelesen, Z. 468-477): Schleife über `approval_handlers()`, `return` beim
ersten Nicht-`Allow`.

Jetzt: **alle** Handler werden genau einmal in Registrierungsreihenfolge
befragt; Ergebnis `first_deny.or(first_ask).unwrap_or(Allow)` — also
**Deny (erstes, mit dessen Grund) > AskUser (erste `ItemId`) > Allow**. Kein
Kurzschluss bei `Deny`, damit die Befragungszahl reihenfolgeunabhängig bleibt.

API belegt: `ApprovalDecision { Allow, Deny(String), AskUser(harw_types::ItemId) }`
(`harw-extension-api/src/contributors.rs:334-338`, `#[derive(Debug, Clone)]`,
nicht `non_exhaustive` → erschöpfender `match`); `ExtensionRegistry::
approval_handlers(&self) -> &[Arc<dyn ApprovalHandler>]` (`registry.rs:163`);
Vertrag „`review` seiteneffektfrei“ am Trait (`contributors.rs:311-318`, W0B-07).

**Parallel-Vorprüfpfad** (`preflight_approvals`, turn_loop.rs:1795;
`PreparedApprovals`, :534): ruft bereits `check_approval` je Call auf — die
Aggregation greift dort damit identisch, ohne zweite Implementierung. Doku von
`PreparedApprovals` und `preflight_approvals` ergänzt (Einträge sind
Aggregate). Die Einmal-Befragung je Handler/Call bleibt: Vorprüfung legt das
Aggregat in `prepared` ab, der sequenzielle Pfad verbraucht es per
`prepared.take(position)` (turn_loop.rs ~1460); `CountingApproval`
(Testmodul, `review` zählt je Call-Id) belegt das in den bestehenden Tests
`parallel_preflight_asks_every_handler_exactly_once` u. a.

### Tests (`turn_loop.rs`, Testmodul, neuer Helfer `multi_guarded_session`)

- `check_approval_lets_a_later_deny_beat_an_earlier_ask_user` — früher AskUser +
  später Deny → `Deny("policy")`, jeder Handler 1×.
- `check_approval_allows_only_when_every_handler_allows` — Allow + Allow → Allow.
- `check_approval_keeps_the_first_ask_user_over_allow_and_later_requests` —
  AskUser + Allow (+ späteres AskUser) → AskUser mit **erster** `ItemId`.
- `parallel_preflight_aggregates_a_later_deny_over_an_earlier_ask_user` — über
  `run_turn` mit zwei parallel-sicheren Calls: Ergebnis `Completed` statt
  `AwaitingApproval`, 1 Ausführung, jeder Handler je Call genau 1×.

## Verhaltensänderung (für Release-Notes / Nutzer)

Im Standardmodus `Delegated` **fragen jetzt nach**: `plan`, `goal`, `explore`,
`research_deps`, `research_web`, `analyze`, `diff` (und ein etwaiges
Fremdwerkzeug namens `mode`). Folgen:
- TUI-Root: Operator-Prompt vor jeder dieser Operationen.
- One-Shot-Root (`harw chat "<prompt>"`, keine Pause möglich): ein solcher
  Aufruf endet in `AwaitingApproval` = Abbruch statt stiller Ausführung.
- `FullAccess` bleibt unverändert (nichts fragt); `AlwaysAsk` unverändert.
- Planner-Rolle bewirbt/admittiert `plan`/`goal` nicht mehr (hatte im Kind nie
  einen Executor).
- Mehrere Handler: ein später registriertes `Deny` (z. B. `ConfigApprovalPolicy`
  `[policy].require_approval_for` … bzw. jede Deny-Politik) schlägt jetzt ein
  früheres `AskUser` der `DefaultApprovalPolicy`; der Nutzer wird dann nicht
  mehr gefragt, der Call wird abgelehnt.
