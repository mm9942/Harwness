## 2. Empirische Befunde (nur bwrap/prlimit ausgeführt, kein cargo)

1. **NPROC 256 ist unbrauchbar.** Nutzer `mia`: 109 Prozesse, 571-759 Tasks (Threads).
   `prlimit --nproc=256 sh -c /bin/true` → „Cannot fork“; `prlimit --nproc=256 bwrap …` →
   „Creating new namespace failed: Resource temporarily unavailable“. `RLIMIT_NPROC` zählt
   alle Tasks der realen UID; beim userns-Anlegen wird das Erzeugerlimit zur Obergrenze der
   Eltern-Ebene. Mit `--nproc=2048` bzw. `4096` läuft es. **Default daher 4096** (Abweichung
   vom Vorschlag 256, begründet; Nutzerlimit hier 32072).
2. Voller Default-Start `prlimit --as=2147483648 --cpu=60 --fsize=268435456 --nofile=256
   --nproc=4096 -- /usr/bin/bwrap … --size 268435456 --tmpfs /tmp …` → `/proc/self/limits`
   zeigt Soft=Hard für alle fünf Limits, `df -B1 /tmp` = 268435456, `/proc/self/fd/0 ->
   /dev/null` bei stdin null, rc 0.
3. **Baum-Kill:** `prlimit … bwrap --die-with-parent --new-session --unshare-all … sh -c
   'setsid sleep & nohup sleep & sleep'`, dann SIGKILL an die äußere PID → keine `sleep`
   übrig. SIGKILL auf das direkte Kind genügt also (kein Prozessgruppen-Kill nötig/möglich:
   `--new-session` löst die Sandbox ohnehin aus der Gruppe; `killpg` bräuchte libc/unsafe).

## 3. Umsetzung je Aufgabe

### 3.1 Speicher-DoS (F-060)
- `capture.rs:34` `BoundedCapture`, `:91` `drain`: liest stdout/stderr gleichzeitig per
  `tokio::select!` (`:114`) mit je 8-KiB-Puffer (`:20`), behält insgesamt höchstens
  `limit + 1` Bytes (gemeinsames Budget = bestehender `max_output_bytes`, Default 64 KiB)
  und kehrt mit `DrainEnd::LimitExceeded` zurück, sobald mehr als `limit` gelesen wurde –
  ohne auf EOF der anderen Pipe zu warten. Speicher ≤ `limit + 1 + 16 KiB`.
- Puffer liegen im Struct, nicht im Future → bei Timeout-Abbruch bleibt Teilausgabe erhalten
  (read ist cancel-safe, zwischen read und push kein `.await`).
- `exec.rs:380` Drain unter `timeout_at(deadline)`, danach `child.wait()` unter derselben
  Deadline (`:406`) – das Timeout umfasst Lesen **und** Warten.
- Überlauf (`:395`): `terminate` (SIGKILL + Reap ≤ 5 s, `:497`, `KILL_REAP_TIMEOUT` `:68`),
  Ergebnis JSON mit `truncated: true`, Marker `[...truncated...]`, neues Feld
  `killed_by_output_limit: true`, `exit_code: -1` (`completed_output` `:443`).
- Timeout: `ToolOutput::error` mit „timed out after Ns; process tree killed. Partial output
  (truncated: …)“ plus `[stdout]`/`[stderr]` im selben Budget (`timeout_output` `:470`).
- Die bestehende UTF-8-sichere Kürzung `truncate_combined_output` (stdout-Priorität) bleibt
  die letzte Stufe.

## 5. Verhaltensänderungen / Risiken

- JSON von `shell.exec` hat zusätzlich `killed_by_output_limit`. Bei Überlauf jetzt
  `exit_code: -1` statt Exit-Code des (früher fertig gelaufenen) Prozesses.
- Timeout-Fehlertext enthält jetzt Teilausgabe (bis `max_output_bytes`).
- `RLIMIT_AS` 2 GiB kann Programme mit großen virtuellen Reservierungen (JVM, einige
  node/V8-Builds, Sanitizer) scheitern lassen; konfigurierbar über `ShellLimits`.
- prlimit setzt Hard-Limits; liegt ein aktuelles Hard-Limit des Harness **unter** dem
  Konfigwert, scheitert prlimit laut (EPERM, Exit ≠ 0, stderr sichtbar).
- bwrap < 0.7.0 kennt `--size` nicht → laut fehlschlagender Start.
- Fehlen bwrap an festen Pfaden (z. B. nur `/usr/local/bin/bwrap`), wird nicht mehr
  gestartet (gewollt, fail-closed).
