## Befund

1. **G-010/F-154** — `ConfigApprovalPolicy` wurde workspace-weit an genau einer
   Stelle gebaut: `harw-cli/src/main.rs:1657`, innerhalb des `PlanningStartup`.
   Der existiert nur, wenn `[tools.plan].enabled = true`. Wer
   `[policy].require_approval_for` setzte, ohne das Plan-Werkzeug
   einzuschalten, bekam seine Pflichtliste **nie** — eine Konfiguration, die
   mehr Rückfragen anordnet, blieb wirkungslos.
2. **F-018** — Kind-Sitzungen montierten ihre Registry über
   `harw_registry_defaults::assemble_registry_for_project`, die nur die
   `DefaultApprovalPolicy` registriert (`harw-registry-defaults/src/lib.rs`,
   Test `assemble_from_current_dir_smoke`: `approval_handlers().len() == 1`).
   Die Config-Politik des Elternteils erreichte den Fan-out nicht.
3. **G-009** — der Freigabemodus lebt seit W2a in einer `ApprovalModeCell`;
   es fehlte aber die Stelle, die entscheidet, **wer** die Zelle mit wem teilt
   und dass `FullAccess` nie an ein Kind durchschlägt.

## Lösung

`ApprovalChain` ist der eine Ort, der die Kette eines Laufs bildet
(Reihenfolge Config → Default → Responder) und die Kind-Ableitung besitzt.
Die Reihenfolge ist Dokumentation, keine Priorität: `check_approval`
aggregiert seit W1-05 `Deny` > `AskUser` > `Allow` über **alle** Handler; ein
zusätzlicher Handler kann deshalb nur einschränken, nie lockern.

### Exakte öffentliche Signaturen (für W2C-01)

```rust
// harw-runtime/src/approval.rs
pub const CONFIG_POLICY_LABEL: &str = "config-policy";
pub const DEFAULT_POLICY_LABEL: &str = "default-policy";

#[derive(Clone)]            // Debug ist von Hand implementiert
pub struct ApprovalChain { /* private Felder */ }

impl ApprovalChain {
    #[must_use] pub fn for_root(
        config: &harw_config::ResolvedConfig,
        mode: harw_extension_api::approval_mode::ApprovalModeCell,
        responder: Option<std::sync::Arc<dyn harw_extension_api::ApprovalHandler>>,
    ) -> Self;
    #[must_use] pub fn for_child(&self) -> Self;
    #[must_use] pub fn handlers(&self)
        -> Vec<std::sync::Arc<dyn harw_extension_api::ApprovalHandler>>;
    #[must_use] pub fn install(
        &self,
        builder: harw_extension_api::ExtensionRegistryBuilder,
    ) -> harw_extension_api::ExtensionRegistryBuilder;
    #[must_use] pub fn snapshot(
        &self,
    ) -> Vec<(&'static str, harw_extension_api::contributors::ApprovalHandlerKind)>;
    #[must_use] pub fn mode(&self) -> &harw_extension_api::approval_mode::ApprovalModeCell;
    #[must_use] pub fn config_policy_tools(&self) -> Vec<String>;
}
```

`snapshot()` liefert genau `RightsSnapshot::approval_chain`,
`config_policy_tools()` genau `RightsSnapshot::config_policy_tools`
(`harw-runtime/src/spec.rs:248-271`). `install` nimmt den Bauer per Wert,
weil `ExtensionRegistryBuilder::approval_handler` `self` verbraucht
(`harw-extension-api/src/registry.rs:495`); vorhandene Handler bleiben vorne
stehen.

### Entscheidungen

- **Config-Politik ohne jeden Nebenschalter.** `for_root` baut sie genau dann,
  wenn `config.harness.policy.require_approval_for` nicht leer ist. Leere
  Liste ⇒ **kein** Handler: ein Handler, der alles durchwinkt, wäre nur
  Rauschen in Kette und Snapshot (und in `approval_handlers().len()`).
- **Kind-Modus: senken, nicht ersetzen.** `for_child` nimmt
  `mode.detached()` und senkt **nur** `FullAccess` auf `Delegated`;
  `AlwaysAsk` bleibt erhalten. Die Vorgabe lautete „Default mit
  `mode.detached()` auf `Delegated` gesetzt (FullAccess wird NIE vererbt)" —
  ein bedingungsloses `set(Delegated)` hätte einen Root in `AlwaysAsk` im Kind
  **gelockert**. Die Klammer ist die eigentliche Zusage, und Monotonie
  (Kind ⊆ Eltern) ist dieselbe Regel wie bei `SessionActivation::intersect`.
  **Bewusste, dokumentierte Abweichung vom Wortlaut** — bitte im Review
  bestätigen.
- **Kein Responder im Kind.** Kinder und Job-Worker haben keine Fläche, an der
  eine Antwort ankäme. Wie ein `AskUser` dort endet, entscheidet die
  `AskResolution` des Einstiegs (`RejectTurn`/`BlockJob`/`Fail`) — nie ein
  stilles `Allow`. Als Rustdoc an `for_child` festgehalten.
- **Labels vergibt die Kette.** `ConfigApprovalPolicy` und
  `DefaultApprovalPolicy` überschreiben `ApprovalHandler::label`/`kind`
  nicht (Defaults: `"unnamed"` / `Other`, `harw-extension-api/src/
  contributors.rs:318-332`). Da beide außerhalb des Schreibbereichs liegen,
  benennt `snapshot()` die beiden bekannten Plätze selbst
  (`CONFIG_POLICY_LABEL`/`ConfigPolicy`, `DEFAULT_POLICY_LABEL`/`DefaultPolicy`)
  und fragt nur den Responder nach `label()`/`kind()`. **W2c-Folgearbeit:**
  `kind()`/`label()` in beiden Politiken überschreiben, dann kann `snapshot()`
  durchgehend die Handler fragen.
- **Zusatzfeld `config_tools: Vec<String>`** neben den vier vorgegebenen
  Feldern: `ConfigApprovalPolicy` bietet keinen Lesezugriff auf ihre Liste
  (nur `requires_approval(&ToolCall)`, `harw-core/src/policy.rs:35`), und
  `harw-core` ist nicht im Schreibbereich. Die Namen werden sortiert und
  dedupliziert abgelegt (stabiler Snapshot; `ConfigApprovalPolicy` nutzt
  intern ohnehin ein `BTreeSet`).

## Offene Punkte für W2c

1. `kind()`/`label()` in `ConfigApprovalPolicy` und `DefaultApprovalPolicy`
   überschreiben; danach kann `snapshot()` die Labels aus den Handlern lesen
   und die beiden Konstanten entfallen.
2. `harw-cli`/`harw-tui` auf `ApprovalChain` umstellen; `PlanningStartup`
   darf die `ConfigApprovalPolicy` dann nicht mehr selbst bauen (sonst steht
   sie doppelt in der Kette — harmlos, aber irreführend im Snapshot).
3. Der Spawner muss `for_child()` tatsächlich aufrufen und die Kind-Kette in
   die Kind-Registry installieren; solange `assemble_registry_for_project`
   der einzige Weg ist, bleibt F-018 in der Praxis offen.
